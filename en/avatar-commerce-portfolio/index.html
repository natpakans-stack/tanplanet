AI Avatar Live Commerce Platform

The problem

Why can't SME shops keep a live stream going "continuously" when every live hour is a chance to sell?

Human hosts can only stream so long. They need breaks, nobody is around after hours, and many small shops have no host at all. Every hour without a stream is sales that simply disappear. Meanwhile most AI avatar tools on the market can only "record a video", not "go live", and they have no commerce loop: they can't answer live comments, switch products or close a sale

The starting brief, before building the AI avatar live platform (positioning: support the host, not replace them)

Hosts can only stream limited hours

People need rest and sleep, so streaming after hours or late at night is almost impossible. Idle hours with no stream are demand left on the table, especially for shops without a regular host

Multiple host shifts are expensive

Covering the whole day means hiring several people across shifts, which SMEs can't afford. So they only stream at certain times and miss the hours with good traffic but no host

Comments pile up faster than anyone can answer

At peak, dozens of customers ask about price, stock and promotions at once. A slow answer loses the sale, and a wrong or overstated claim about a product carries legal risk

AI avatar tools are async, not live

Existing avatar video tools can't interact in real time and have no live commerce loop (product switching, CTA timing, live comment replies), so they can't close sales on a real live stream

Many shops and workspaces, data must stay strictly separate

A platform where an agency manages many clients can't leak even one row across shops. Doing isolation by hand is easy to get wrong and hard to audit

Ideate

The solution

Don't build a new AI core. Build on the existing Avatar Engine and fill in what's missing to close the live commerce loop

Integration layer on top of the Avatar Engine

The existing engine already has TTS / lip-sync / render / RAG. The AI avatar live platform wires the trigger logic, feeds script and product context, and manages the session lifecycle, without rebuilding a duplicate avatar core

Live Studio for scene setup + streaming from real devices

Compose scenes, layers and products free-form on one canvas, then broadcast from the shop's own devices (phone-as-camera). The avatar speaks from a script tied to each product

Auto-reply pipeline with a Risk Filter

Comment → intent detection → Risk Keyword block before replying → Reply Burst priority queue (price/stock jump ahead) so the avatar answers live within a set latency budget

Live Console real-time (SSE)

Managers watch avatar status, stream health, the comment feed and the risk panel live, through an SSE stream that survives reconnects, keeps order and drops duplicate events

Multi-tenant data isolation at the database level

Every query is bound to workspace_id, with Postgres RLS as the last line of defense (Model B tenancy: authority lives in a central hub, identity is handled separately by Zitadel). Isolation is non-negotiable and covered by negative tests

Why this stack?

NestJS 11 + Fastify: the Live Orchestrator is a long-running process (route handlers don't fit), and DI with one module per feature lets the team scale · Drizzle ORM: TS-first, the schema is TypeScript so it matches FE type sharing, and it stays close to raw SQL, which suits multi-tenant queries and audits · PostgreSQL + RLS: 100% data isolation at the database level · Zitadel (identity) + Model B tenancy: identity is separated from workspace/entitlement authority (which lives in the central hub) · pnpm workspaces + OpenAPI → generated client (with a contract drift gate in CI): type safety across packages without a complicated build matrix

Test & Iterate

Hacking the problems

6 engineering problems I had to design solutions for: multi-tenancy, real time, integration lifecycle

Not a single row can leak across workspaces

Agencies see many shops in one dashboard. One badly scoped query leaks data across clients, which is non-negotiable

Fix: enforce workspace_id scoping on every query + Postgres RLS as the last line of defense in the DB, an ESLint guard that blocks unscoped queries, and a negative isolation test proving nothing leaks. Isolation is part of the Definition of Done, not left for hardening at the end

Who owns tenancy data? (Model B)

The ecosystem has several products. If each one stores its own workspaces, memberships and subscriptions, they drift out of sync and entitlements go wrong

Fix: clear separation of duties. The central hub is the authority for tenancy/entitlement (resolving the workspace + verifying permissions through the Hub API), Zitadel handles identity (login) only, and the AI avatar live platform mirrors memberships locally. A Prism mock of the Hub means devs don't have to run the real hub every time

Comments pile up, but the avatar can only answer one at a time

At peak, dozens of comments arrive at once. It can't, and shouldn't, answer all of them. It has to pick the important ones first within a limited time budget

Fix: a Reply Burst priority queue. Price/stock (P1) jumps ahead of chit-chat (P3), capped at ≤6 per batch, and a per-script TTL drop discards comments that have waited too long once the next script starts. The queue stays small and replies land at the right moment

The Console has to be live, but connections keep dropping and reconnecting

Mobile live streams have shaky connections. If the stream drops and events go missing, repeat or arrive out of order, the manager reads the wrong status and makes the wrong call

Fix: design the SSE console stream to auto-reconnect, keep ordering, dedupe repeated events and apply backpressure when the client falls behind. The reliability contract is written as a separate NFR, not best-effort

Integrating with external engines and services that don't exist yet

The Avatar Engine, comment source and some Hub endpoints weren't ready when development started. Waiting for them before writing the integration would block the whole pipeline

Fix: contract-first. Write network-free contract tests from the spec first (red-first even while the implementation is pending), run an OpenAPI/contract drift gate in CI Tier 1 on every PR, and use Prism mocks so devs can work in parallel without the real services

The engine caps sessions at 20 minutes, but the live stream must keep going

The Avatar Engine closes a session every 20 minutes. If it just ends, the picture stutters and the audio cuts out, and viewers notice immediately

Fix: the AI avatar live platform manages the session lifecycle. It preloads the next session ≥90s before the cap (or ≥30s before a scene switch) and does a seamless handover within a budget of audio ≤200ms / visual ≤100ms while keeping pose continuity. Viewers never know a session switched behind the scenes

Deliberate design decisions

What I chose "not to build" matters as much as what I built

The AI avatar live platform doesn't build a new avatar core. TTS, lip-sync, render, RAG, ≤2s latency and GPU pooling already exist in the Avatar Engine, so the focus is the integration layer: orchestration + the commerce loop + a multi-tenant back office + a real-time console. The positioning was sharp from day one: support the host, not replace them, unlocking hours people can't cover. A clear scope means a focused implementation that's easy to maintain

Level Up · Reflect

Knowledge domains that got stronger

5 areas where my level genuinely moved up through this project

1. Multi-tenant SaaS architecture, from "knowing the concept" to "designing isolation I can prove":

I now understand layered data isolation: workspace_id scoping in the application, Postgres RLS in the database, an ESLint guard that catches mistakes while writing code, and negative tests proving nothing leaks, plus the tenancy authority split (Model B: authority in the hub, identity in Zitadel). Lesson: good isolation is several testable layers, not good intentions

2. Real-time systems — latency budget, priority queue, stream reliability:

I designed Reply Burst as a priority queue (P1/P2/P3 + TTL drop) so replies land on time within the latency budget, and an SSE console stream that survives reconnects, keeps ordering, dedupes and applies backpressure. Lesson: reliable real time means designing the failure modes (drops, duplicates, falling behind) from the start, not best-effort

3. Monorepo + contract-driven development:

I set up pnpm workspaces (apps + shared packages: db/auth/types/api-client/engine-contracts), generated the client from OpenAPI with a drift gate, and wrote network-free (red-first) contract tests against external services that didn't exist yet. Lesson: a contract is the agreement that lets teams and services move in parallel without blocking each other

4. Integration architecture, an adapter over a 3rd-party engine + session lifecycle:

I designed a layer that wraps the existing Avatar Engine without touching its core, handling preload/handover so the 20-minute session cap looks continuous (audio ≤200ms / visual ≤100ms / pose continuity), with an adapter pattern ready for new providers. Lesson: making existing pieces fit "seamlessly" is harder than writing from scratch, and worth far more

5. Backend engineering with NestJS + Fastify + Drizzle:

I laid out one module per feature (21 modules) + DI, chose Fastify because the Live Orchestrator is a long-running process, and used Drizzle (a TS-first ORM close to raw SQL) with migration discipline (versioned · idempotent · fail-loud when the schema doesn't match). Lesson: structure enforced by conventions + guards lets a solo dev run a large system without it falling apart

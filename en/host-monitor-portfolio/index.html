Live Commerce Host Monitor

Internal computer vision research that replaces hours of rewatching streams with live KPIs readable second by second. Built from validated pretrained models, calibrated against bias with multimodal fusion, and designed around the privacy of the people being measured.

Mar 11, 202611 min read

SHARE

An internal R&D prototype that chains 4 computer vision models into one pipeline: detect faces in a live stream (a live commerce platform), recognize who they are, read 7 emotion classes, measure engagement (smiling, talking, looking at the camera), then summarize it as live KPIs and a session report, so the team sees the big picture without rewatching the video.

Empathize · Define

The problem

A single live commerce session runs for hours. How do you know when the host still has energy and where engagement drops, without rewatching the whole thing?

The ops team wanted to understand how engaged each host is with the camera and how their mood shifts across a session. Having someone rewatch hours of video and score it by hand is slow, always late and subjective. The brief: make these metrics readable second by second, automatically, while respecting the privacy of the people being measured.

— The starting brief for the host analysis research

Streams run for hours, too long to rewatch

A selling session lasts hours. Nobody rewatches the whole clip to assess engagement. The team needed per-second metrics that summarize instantly.

"Is the host losing energy?" Human eyes can't keep up

A host's mood and activity change constantly. Scoring by eye is subjective and patchy. We wanted a signal that can be measured as a number.

Off-the-shelf FER models are biased

Emotion models trained on standard datasets tend to read a neutral or talking face as sad or angry. Used as-is, the numbers are wrong from the start.

Knowing who is on screen means preparing photos in advance

Typical face recognition needs a set of reference photos for each person first. That is a hassle when several hosts rotate in and out. We wanted to register people live, on the spot.

Faces and emotions are sensitive biometric data

Processing face embeddings and personal emotions counts as biometric data under PDPA (Thailand's data protection law). Without designing for consent, retention and storage from day one, it becomes a liability.

Ideate

The solution

Let a CV pipeline do the heavy lifting: detect, recognize, read emotion and measure engagement on every frame, then summarize it as KPIs a person can read in 3 seconds

Real-time pipeline: face → identity → emotion → engagement

Every frame runs continuously through MTCNN (finds faces) → FaceNet (identity embedding) → ViT (7 emotion classes) → MediaPipe FaceMesh (smiling, talking, looking at camera)

Readable KPIs with a rolling window

The output is Energy / Smile / Talking / Looking / Mood with 1-minute and 5-minute moving averages, so you can see live whether things are trending up or down

Click-to-enroll: register identities live

Click a face in the video, type a name, press Enter. The embedding is averaged into a file and works immediately. No reference photo set needed in advance.

Multimodal calibration to correct a single model's bias

Geometric signals from FaceMesh (smile and frown blendshapes) gate the ViT output, so neutral faces stop reading as sad and real smiles come through more clearly

Local-only and PDPA-aware by design

Face embeddings and all logs stay on the machine (gitignored) and are never sent out. Consent, retention windows and access limits were planned from the start.

Test & Iterate

Hacking the problems

6 problems I had to solve myself: ML model bias, hardware quirks and real-time engineering

My own trained model read neutral faces as "angry"

The classifier fine-tuned on a public dataset had heavy class imbalance (one class had many times more images than another). On a real webcam it leaned toward the class with the most data, and neutral faces were read as angry with high confidence.

Fix: comparing per-class recall and testing live made the failure mode obvious, so I switched to a pretrained ViT (FER+) trained on a larger, more balanced dataset. Lesson: see point 2 in Knowledge Domain.

ViT still got stuck on "sad" for normal talking faces

The pretrained ViT was better, but it still stuck to negative emotions on neutral and talking faces, which pushed the mood score too negative.

Fix: use geometric signals from FaceMesh (frown and smile blendshapes) to "gate" the ViT output. With no evidence of a frown, negative emotion probabilities are damped; with a real smile, happy is boosted. Together this is a multimodal calibration that beats a single model's bias.

Emotion labels flickered from frame to frame

Reading each frame independently made labels jump between happy, neutral and sad constantly, and face identities swapped when people moved.

Fix: match faces across frames with IoU tracking so each face keeps a stable track id, then smooth the probability vector with an EMA per track. Labels settle, and metrics accumulate on the right person.

Face recognition needed a photo set before it worked

Standard identification needs reference photos of each person ahead of time. That breaks down when hosts change often.

Fix: click-to-enroll. The operator clicks a face in the live video, types a name and presses Enter. The system averages that frame's embedding into a file, and recognition works right away with no prior photo set.

Capturing the stream and pulling comments at the same time was hard

I wanted both the live video (to read faces) and live metadata (comments, gifts, viewers) in one app, without relying on hard-to-access APIs.

Fix: Electron WebContentsView embeds a real browser to open the stream → frames are captured and sent to the models, while a live-comment connector reads comment, gift, like and join events live. The view is kept positioned over a React placeholder at all times.

The face detector was the bottleneck, and it hit an MPS bug

Face detection was the slowest step in the pipeline, and the detector also hit an Apple MPS bug (pooling needs evenly divisible sizes) that made it hang.

Fix: pin the detector to the CPU to avoid the bug, run embedding and emotion on MPS, detect every other frame and process asynchronously over WebSocket. The result is about 8–12 FPS on an Apple M4 Pro, enough for live monitoring.
Define

Deliberate design decisions

Because this touches people's biometric data, what the system does not do matters as much as what it does

This is a research prototype that captures biometric data (face embeddings) and behavioral data (emotion and attention), so it was designed around PDPA principles from the start. All data stays on the machine and is never exported. The metrics are "signals" for an overview, not fixed judgments about a person, and the docs state the models' limitations and biases clearly. A real production version would always need consent, a retention window and access limits first.


Local-only, always

Level Up · Reflect

Knowledge domains that got stronger

5 areas where my skills actually moved up through this project

1. Real-time computer vision pipelines: orchestrating several models to keep up with the frame rate:

I chained 4 models (detect → recognize → classify → mesh) to run within a single latency budget, including IoU tracking across frames and EMA smoothing. Lesson: real-time ML is a game of latency and output stability, not just a single model's accuracy number.

2. Model evaluation & the accuracy trap: headline accuracy can lie:

My own trained model had a nice top-1 score on the test set but failed in real use, because the test set inherited the class imbalance from training. Only per-class recall, a confusion matrix and live testing revealed the failure mode (neutral → angry). Lesson: one headline number can always hide a distribution problem.

3. Pretrained vs custom-trained: knowing when to train your own:

A direct comparison showed that a small CNN trained on a few thousand images can't compete with a ViT pretrained on a large dataset. Lesson: training your own is only worth it when (a) the label set is non-standard, (b) there is a measurable failure mode in the real domain, or (c) you have a data flywheel feeding it. Otherwise, pretrained is the right default.

4. Multimodal signal fusion: combining different signals beats a single model's bias:

Learned emotion from ViT is blended with geometric blendshapes from FaceMesh through a gate/bias/boost mechanism to cancel out the bias a single model has. Lesson: when one model is biased, adding an independent signal is often more robust than forcing a fine-tune of the same model.

5. Applied AI ethics / PDPA: responsible AI is a requirement, not a nice-to-have:

I designed a system that touches biometrics and emotion with consent, retention, local-only storage and documented model bias in mind from the start. Lesson: with sensitive personal data, ethical and legal correctness is a system requirement, not an add-on for later.
